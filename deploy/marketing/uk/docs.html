Архітектура

BidShard — self-hosted ПЗ, яке ви встановлюєте на свій VPS або dedicated-сервер. Ця сторінка описує, що саме працює на вашій інфраструктурі — а не cloud SaaS control plane. Інженерні деталі для контрибʼюторів — у vendor tree (docs/ARCHITECTURE.md).

Огляд

Система поділена на hot path (прийняти або відхилити кліки й impressions за мілісекундні бюджети) і cold path (CRUD кампаній, billing, звіти, ML batch jobs, outbox workers). У дефолтній моделі доставки ваш трафік не проходить через сервери BidShard — лише license JWT і support chat залишаються на стороні вендора.

Hot path
Відвідувач → Nginx edge → tracker → Filter + debit → Redis / broker
Async
processor → Postgres + ClickHouse
Admin
control :8188 API, outbox, billing — не на ingest-потоці

HTTP 202 на /track означає, що tracker прийняв і провалідував подію на ingest path. Це не означає, що Postgres або ClickHouse уже записали рядок — це відбувається асинхронно через processor.

Стек за замовчуванням на вашому сервері

Типовий інстал на одному VPS запускає такі процеси (systemd units з installer):

Процес Роль Порт за замовч.
Nginx (OpenResty) TLS, rate limits, ранній blacklist, shard routing до пулу tracker 8180 / 443
tracker Ingest кліків і impressions, filter chain, budget enforcement, async enqueue подій 8181–8184
control Admin API, мутації кампаній, outbox workers, payment webhooks 8188
processor Читає Redis streams (або broker WAL) → settle Postgres + batch у ClickHouse 8186
PostgreSQL Фінансова правда: кампанії, бюджети, ledger, outbox 5430 (compose default)
Redis Hot-path debit/dedup, streams, pub/sub reload конфігу 6479+ (sharded)
ClickHouse Аналітика, fraud/IVT звіти, ML feature reads (cold path) 9000

Перевірка ліцензії — offline Ed25519 JWT файл на диску; без регулярного phone-home для ingest tokens. Feature flags, host activations і export limits закодовані в JWT per SKU. Кампанії та обсяг подій не обмежуються ліцензією, коли в каталозі стоїть 0.

Що відбувається на кліку

  1. Edge (nginx) — опційний ранній reject: per-campaign rate limit, circuit breaker, IP blacklist, ASN policy. Конфіг дзеркалиться в worker memory по таймеру; access phase не викликає Redis на кожен request.
  2. Tracker parse — HTTP/1 обробляє gnet (не net/http на hot path). /track вимагає Content-Length; chunked bodies відхиляються (parity з edge policy).
  3. Local filters — license, geo, schedule, device signals, consent і rule-based fraud checks працюють in-process. ML inference тут не запускається; tracker може читати precomputed fraud-boost snapshot з Redis, якщо ваш tier це включає.
  4. Redis unified filter — максимум один синхронний Lua script на прийняту подію для budget debit і dedup (нуль scripts, коли eligible local-quota full-skip mode). Campaign keys використовують Redis hash tag, щоб multi-key atomicity залишається на одному shard master.
  5. Async enqueue — прийняті події йдуть у Redis stream або опційний mmap broker WAL через reserved slot у producer queue. Якщо enqueue падає після debit — budget відкочується.
  6. processor — background workers батчать у Postgres (settlement) і ClickHouse (analytics).

/click прогоняє ту саму filter chain і повертає redirect. /openrtb/bid запускає in-process RTB auction — без повної filter chain (тариф Network, live mode).

Antifraud semantics (без маркетингових скорочень)

  • Hard reject — HTTP 403; бюджет не списується.
  • Silent reject — HTTP 202 відвідувачу (decoy accept); прапорець у analytics, щоб воронки залишались чистими. Не змінює campaign settings у Postgres автоматично.
  • IVT detector (Pro+) — batch rules на ClickHouse; може enqueue blacklist/boost actions через admin outbox.
  • ML fraud scorer (Scale+) — batch LightGBM у sidecar; пише boost keys, які Redis синхронізує в tracker snapshot. Не per-click inference на ingest.

Admin, billing і звіти

control — modular monolith: один процес віддає /api/v1/* і крутить in-process workers. Коли ви PATCH-ите кампанію, мутація і рядок outbox_events пишуться в одній Postgres transaction. Outbox worker (poll ~20 ms) застосовує Redis side effects і тригерить tracker registry reload через pub/sub.

tracker не опитує Postgres на кожен request — читає in-memory snapshot, оновлений з Redis. Payment webhooks і ledger entries — лише cold path; processor не вставляє рядки balance_ledger.

Сховища даних

PostgreSQL

Кампанії, бюджети, team RBAC, payment state, transactional outbox. Джерело фінансової правди після processor settlement.

Redis

Per-shard budgets, dedup locks, ingest streams, fraud blacklists, ML boost snapshots. Standalone masters + Sentinel — не Redis Cluster на hot path.

ClickHouse

Event analytics, report aggregates, IVT/ML feature reads. Не консультується синхронно на accept /track.

Кампанії sharded: slot = CRC32C(campaign_id) & 1023 мапить на Redis shard і tracker listener. Edge slot map і Go мають бути в sync (installer публікує map).

Чесні обмеження

  • Ми не хостимо ваш трафік і не гарантуємо uptime на вашому VPS — сервером керуєте ви.
  • Edge і XDP можуть дропати відомі bad IP; rotating proxies все одно можуть дійти до tracker — там працюють L7 rules.
  • BROKER_SHADOW_MODE shadow-ить лише processor CH ingest; tracker WAL writes live, коли увімкнено broker-primary.
  • LOCAL_QUOTA_MODE=shadow проганяє local quanta, але все одно виконує sync Redis Lua; лише live може його пропустити, коли eligible.
  • Обмеження JWT SKU (хости, tenants, features, export chunk) застосовуються — див. тарифи і deploy/vendor/sku.yaml.
